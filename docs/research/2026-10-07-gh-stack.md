# gh-stack 조사와 workflow 적용 제안

조사일: 2026-10-07. GitHub 공식 문서·Changelog·CLI 소스와 릴리스만 사용했다. CLI를 설치하거나 실제 PR/stack을 만들지는 않았다.

Context7에서 `/github/gh-stack`을 resolve한 뒤 에이전트 실행과 서버 merge 동작을 조회하고, 최신 공식 공지·소스로 교차 확인했다. 로컬 환경은 `gh 2.102.0`, `Git 2.54.0`이며 `gh extension list`에는 설치된 extension이 없었다.

## 결론

GitHub Stacked PRs는 **2026-10-06 GA**, 최신 CLI는 **2026-10-02 배포 v0.2.0**이다. 서버 GA 변경과 이전 CLI 문서를 구분해서 적용해야 한다. [GA 발표](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/), [CLI 릴리스](https://github.com/github/gh-stack/releases/tag/v0.2.0)

`github-workflow`에 의존 관계가 있는 여러 PR을 위한 **선택 경로**로 넣기 적합하다. `git-workflow`에는 도구 전체를 중복 설명하기보다 서명·DCO·히스토리 재작성·worktree 안전 조건과 GitHub workflow로의 연결을 둔다. 이는 조사 결과를 바탕으로 한 설계 제안이며, 이번 조사에서는 기존 스킬을 수정하지 않았다.

예를 들어 `main ← schema ← api ← ui`를 PR 세 개로 나누면 각 PR은 해당 단계의 diff를 보여 준다. CLI는 브랜치 생성, 연쇄 rebase, push, PR 생성과 GitHub의 실제 Stack 연결을 담당한다. 일반 chained PR과 GitHub Stack에 등록된 PR은 merge API와 서버 동작이 다르므로 별도 경로로 설명해야 한다. [공식 개요](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs), [공식 APIs](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests-apis-and-webhooks)

GitHub의 native Stack 생성에는 PR이 최소 두 개 필요하다. CLI는 한 branch도 로컬 Stack으로 추적하고 PR로 제출하지만, PR이 두 개 미만이면 서버 Stack 생성 단계를 건너뛴다. [v0.2.0 submit의 최소 PR 조건](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/cmd/submit.go#L802)

## 설치·권한·적용 범위

```sh
gh extension install github/gh-stack
gh extension upgrade stack
```

인증된 GitHub CLI와 push 가능한 저장소가 필요하다. 최소 버전 안내는 현재 서로 다르다. 최신 Quickstart는 `gh 2.90.0+ / Git 2.20+`, v0.2.0 README는 `gh 2.0+ / Git 2.36+`를 적는다. worktree 기능을 포함한 운영 기준은 보수적으로 **Git 2.36+와 최신 gh**를 사용하는 편이 맞다. 이 차이는 문서 불일치로 남아 있으며 호환성 테스트로 확인하지 않았다. [최신 Quickstart](https://docs.github.com/en/pull-requests/get-started/stacked-prs-quickstart), [v0.2.0 README](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/README.md#installation)

Stacks REST API는 fine-grained PAT뿐 아니라 GitHub App user/installation token도 지원한다. 조회는 `Pull requests: read`, 생성·추가·해제는 `Pull requests: write`; async merge는 `Contents: write`가 필요하다. 공개 리소스의 조회는 인증 없이도 가능하다. 따라서 과거 preview의 PAT 전용 안내를 가져오면 안 된다. Git push는 별도 Git 인증과 저장소 쓰기 권한을 필요로 한다. [Stacks 권한](https://docs.github.com/en/rest/pulls/stacks), [async merge 권한](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously)

모든 stack branch는 **같은 저장소**에 있어야 하며 cross-fork stack은 지원하지 않는다. 포크에서 upstream으로 보내는 일반 오픈소스 PR에 보편 기본값으로 적용하기 어렵다. GitHub Desktop도 지원하지 않는다. GHES 지원 버전은 아직 발표되지 않았다. [공식 적용 범위](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs#where-can-you-use-stacked-pull-requests), [GHES 예정](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/)

## 에이전트에 맞는 명령과 주의할 부작용

공식 `gh-stack` 스킬이 이미 제공된다. 전체 내용을 복사하기보다 프로젝트 정책과 충돌하는 부분만 조정하고 상세 command reference를 연결하는 것이 유지보수에 유리하다. upstream skill에는 `metadata` frontmatter가 있으므로 이 저장소의 frontmatter 규칙에 맞추지 않고 그대로 vendoring할 수는 없다. [upstream skill](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/skills/gh-stack/SKILL.md)

- 상태 읽기: `gh stack view --json`. bare `view`는 PTY에서 TUI를 열 수 있다.
- 생성: `gh stack init <branch>`, `gh stack add <branch>`처럼 이름을 지정한다.
- 제출: `gh stack submit --auto`는 모든 활성 branch를 push하고 draft PR을 생성한다. `--open`은 신규뿐 아니라 기존 PR도 ready로 만든다. 제목/본문은 자동 생성되므로 제출 후 `gh pr edit --title/--body-file`로 작성한다.
- 하위 branch 수정: owning layer에서 수정·commit 후 `gh stack rebase --upstack`, 상태 확인 후 push한다.
- `gh stack modify`는 **TUI 전용**이며 headless 재정렬 경로가 없다. 복구용 `--continue/--abort`는 가능하지만 편집 UI를 에이전트가 bare 실행하면 안 된다.
- 여러 remote가 있으면 쓰기 명령에 `--remote <name>`을 전달한다. remote flag가 없는 checkout/navigation은 `remote.pushDefault` 설정이 필요하다.

근거: [공식 agent skill](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/skills/gh-stack/SKILL.md), [명령 reference](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/skills/gh-stack/references/commands.md)

`sync`는 단순 조회가 아니다. fetch, 서버/local 구성 reconcile, 연쇄 rebase, push, PR/stack 갱신까지 수행한다. 비대화형 local/remote 구성이 갈라지면 **exit 0과 `Sync aborted`**로 끝나므로 exit code만으로 성공 판단을 하면 안 된다. 이후 JSON 상태와 remote 상태를 확인해야 한다. `--prune`은 merged branch를 삭제하므로 별도 필요가 있을 때 사용한다. [sync reference](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/skills/gh-stack/references/commands.md#sync)

`push`와 `submit`은 per-branch `--force-with-lease`를 사용한다. push는 여러 branch 중 일부만 갱신될 수 있고, submit도 앞 단계 push/PR 생성 뒤 후속 단계에서 실패할 수 있다. 원격 히스토리 재작성 정책은 명령 이름에 관계없이 적용해야 한다. `link`는 PR 번호만 연결할 때와 branch 인자를 받아 push/PR 생성/base 수정까지 할 때 부작용이 다르다. [push/submit/link reference](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/skills/gh-stack/references/commands.md)

## 서명과 DCO

`gh stack add -Am` helper는 실제로 `git commit -m`을 실행하며 `-S`와 `--signoff`를 전달하지 않는다. add command에도 이를 지정할 flag가 없다. Git 설정·hook에 따라 서명이 생길 수 있지만 helper 자체가 서명과 DCO를 보장하지 않는다. 이 저장소의 `git-workflow`처럼 둘 다 필수인 정책에서는 다음 패턴을 유지한다. [Commit 구현](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/internal/git/gitops.go#L731), [add flags](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/cmd/add.go#L49)

```sh
gh stack add feature/api
git add <선택한 파일>
git commit -S --signoff -m "feat: add API layer"
```

로컬 rebase helper에도 명시적인 signing/signoff flag가 없다. 따라서 로컬 재작성 후에는 필요한 서명과 trailer가 실제 commit에 있는지 다시 검증해야 한다. GitHub 서버 서명과 개발자 자신의 서명·DCO는 별개다. [rebase 인자](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/internal/git/git.go#L152)

GA 발표에 따르면 서버 `Rebase stack`은 원저자를 유지한 signed replacement commit을 만들며, partial merge 후 자동 rebase도 branch signature 규칙이 있거나 기존 commit에 서명이 있으면 replacement commit을 서명한다. 예전 서버 문서의 unsigned 경고를 현재 전체 동작으로 단정하지 않는다. 로컬 개발자 서명 보존 여부, DCO trailer 검증은 실제 저장소 정책에 맞춰 별도 확인해야 한다. [2026-10-06 변경](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/)

## GitHub native stack의 review·CI·merge

일반 chained PR과 달리 native stack은 모든 layer에서 최종 trunk의 required review/check/CODEOWNERS 규칙을 적용하고 trunk 대상 Actions도 각 layer에서 실행한다. 중간 PR의 direct base만 보고 품질 조건을 계산하면 안 된다. [공식 규칙·CI](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs#rules-ci-and-merging)

native stack에는 기존 수동 가이드의 `gh pr merge` 순차 실행이나 임의 `gh pr edit --base main` retarget를 적용하지 않는다. async merge API가 필요하며 CLI 경로는 `gh stack merge <target> --yes --squash`다. 선택한 PR **및 그 아래 아직 merge되지 않은 PR 전체**가 대상이므로 merge 승인에도 그 범위를 명시해야 한다. `--yes`는 CLI prompt만 생략하며 사용자 권한을 새로 부여하지 않는다. [공식 async API](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests-apis-and-webhooks#merge-api), [native base 변경 제한 안내](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/skills/gh-stack/references/troubleshooting.md)

서버가 자동 retarget/rebase를 수행하므로 merge 후 local `sync`로 상태를 맞춘다. standalone chained PR 경로는 Stack 미등록·cross-fork·지원되지 않는 host 등의 경우에만 별도로 유지한다. [공식 merge 동작](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs#merging)

**v0.2.0 문서와 GA 서버의 차이:**

- CLI 문서는 queue에서 stack이 여러 group으로 나뉠 수 있다고 적지만 GA는 single merge group으로 들어가고 landing한다고 발표했다.
- CLI FAQ는 bypass 미지원이라고 적지만 GA는 권한 있는 사용자가 lowest unmerged PR을 bypass merge할 수 있다고 발표했다. 최신 REST에는 `bypass_rules`가 있다. v0.2.0 CLI가 이 flag를 노출한다고 확인한 것은 아니다.
- CLI FAQ는 auto-merge 미지원이라고 적지만 GA는 앞으로 몇 주 동안 rollout한다고 발표했다. 모든 저장소에 이미 제공된다고 단정할 수 없다.
- 예전 문서는 merge commit 방식이 그룹당 한 commit이라고 적었지만 GA는 PR당 한 merge commit으로 바뀌었다고 발표했다. squash는 기존 source FAQ에서 PR당 한 squash commit으로 설명한다.

근거: [GA 발표](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available/), [최신 REST async parameters](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously), [v0.2.0 FAQ](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/docs/src/content/docs/faq.md)

직접 async merge의 원자성은 최신 공식 API 문서에서 명시한다. 다만 일반 Troubleshooting 문서는 부분 실패 후 하위 PR이 남는 설명을 merge 경로 구분 없이 적고 있어 충돌한다. 규약을 적을 때 직접 merge·queue 요청·최종 queue landing을 구분하고, 실제 결과를 다시 확인한다. 이 조사에서는 서버 merge를 실행해 확인하지 않았다. [공식 API 원자성](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests-apis-and-webhooks#merge-api), [상충하는 troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-stacked-pull-requests#merging-stopped-partway-through-the-stack)

## Worktree와 workflow 적용 위치

v0.2.0부터 metadata는 `<git-common-dir>/gh-stack`으로 공유된다. stack이 여러 worktree에 흩어져 있어도 rebase/sync/modify가 branch 소유 worktree에서 실행된다. dirty/busy/missing worktree는 중단 조건이며 자동 stash나 worktree 생성·제거는 하지 않는다. gh-stack mutation lock은 **gh-stack끼리만** 조율하므로 다른 agent의 Git 명령과 동시에 같은 clone의 history를 바꾸지 않아야 한다. [v0.2.0 릴리스](https://github.com/github/gh-stack/releases/tag/v0.2.0), [worktree 안전 규칙](https://github.com/github/gh-stack/blob/d4ab7ab47e5b3e3708a27c8c42abcdf4bc321419/README.md#git-worktrees)

권장 구현 범위는 다음과 같다.

1. `github-workflow`: 기존 `references/stacked-prs.md`의 적용 범위를 생성·수정·sync·merge로 넓히고 native/manual 분기를 먼저 둔다. native stack 감지, headless 명령, PR 본문 작성, trunk 기준 check, stack merge 범위, 실패 복구를 추가한다. 분량이 커질 때만 CLI 상세를 별도 reference로 나눈다.
2. `git-workflow`: helper commit 사용 대신 `git commit -S --signoff`, implicit force-with-lease 정책, rebase 후 서명 확인, 같은 clone의 작업 직렬화 조건을 둔다.
3. 기존 스킬은 유지하고 upstream skill을 필수 설치로 강제하지 않는다. 서로 독립된 작업을 억지로 stack에 넣지 않는다.
4. 실제 도입 시 임시 저장소 또는 승인된 sandbox repo에서 서명/DCO, native stack 제출, lower-layer 수정, partial merge 후 sync, worktree 충돌 복구를 검증한다. 이번에는 문서·소스 조사만 수행했다.

이 권고는 도구 기능에 대한 사실과 이 저장소의 정책을 결합한 판단이다. 현재 서버 기능을 실제 계정·저장소에서 검증하지 않았고, CLI를 설치하거나 PR을 게시하지 않았다.
